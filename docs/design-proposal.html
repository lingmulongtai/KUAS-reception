第1回・第2回レビューの指示は反映済みです。 反映した指摘には 反映、判断待ちのものには 未決 を付けています。

第2回レビューで反映した内容

feature/round2-flow-and-scoring

  • 友達同士のまとめ受付。 1〜5名を同時に受付し、全員ぶんの空きがあるプログラムだけを選べるようにした。「入れたつもりで入れていない」が起きないので、確認作業そのものが要らない
  • 割り当てを「総合ポイント」に統合。 予約60点＋学年(高3で30点)＋参加回数(1回5点・上限20点)の合計順。配分は管理画面で変更でき、変えた瞬間に待機者リストの並びと各人の内訳が追随する
  • 「説明会のみ」をプログラム選択画面へ移動。 体験のあとに説明会もあることを説明してから選ばせる。完了画面も「午前の説明会の受付が完了しました」に
  • 受付番号の発行。 完了画面に大きく表示。番号を入れると希望選択から再開できる
  • 自動バックアップ。 受付ごとに端末内へ20世代、10件ごとにファイルへ自動書き出し
  • 名簿から直接受付。 行の「この方を受付」で確認画面まで直行
  • プログラム画像をブラウザから登録。 横800pxに縮小して保存（1枚100KB前後）
  • Liquid Glass を削除。 ライト／ダークの2種類に
  • 管理者ログインをパスワードのみに。 メールアドレス欄を削除
  • 不具合修正。 空の名簿を保存してもデモ用の予約者が復活し、実在しない人が定員を消費していた

18 commits · feature/ui-refresh-and-matching

  • 予約者の照合を作り直した。 姓だけ・名だけ・ひらがな・カタカナ・ローマ字・メールアドレス・濁点の打ち漏れ、どれでも引ける。入力しながら候補が出て、同姓は候補から選ぶ。テスト 44 ケースで担保している

フォントは全部リポジトリに同梱済みなので、会場に回線が無くても崩れません。 iPad を来場者に触ってもらう前提で、本文は 15px 相当より小さくしない方針です。

  • 1反映数字を等幅にした。 人数・定員・名簿の各表に tabular-nums を当て、桁が変わっても横幅が動かないようにした
  • 2反映アラビア語を実際に右横書きにした。 html[lang="ar"] の指定は名前とは裏腹に direction: ltr を当てており、左横書きのままだった。html[dir] を切り替える方式に作り直し、メールアドレスや数値だけは左横書きで残している

技術メモ

いただいた技術的な問いへの回答です。判断が要るものは、選択肢と トレードオフを並べてあります。

Next.js のようなフルスタック構成にすれば、データの保持性は上がるか

結論：上がりません。別の手段が要ります

Next.js は React でページを組み立てるためのフレームワークで、それ自体はデータをどこにも保存しません。 保存先は結局のところ「別に用意したデータベース」か「サーバーのファイル」になります。 サーバーを置かずにブラウザだけで動かす構成なら、保存先の選択肢は今と同じ localStorage / IndexedDB / ファイル の3つしかなく、Next.js を挟んでも増えません。

むしろ、いま npm start だけで起動できるものが、ビルド手順と Node の常駐を 必要とするようになります。当日の朝に動かなくなったとき、原因の切り分けが難しくなる方向です。 保持性の問題は、フレームワークではなく保存先を変えることで解きます。

保存先の選択肢と、それぞれの弱点：

保存先容量の目安消える条件採否
localStorage 5〜10MB 履歴削除・シークレット窓・サイトデータ消去 現行。手軽さは随一
IndexedDB 数百MB〜GB localStorage と同じ条件で同時に消える 容量は解決するが、消える問題は解決しない
File System Access API ディスク次第 ユーザーがファイルを消したときだけ 導入済み。これが実質の解
サーバー＋DB 事実上無制限 サーバーが壊れたとき LAN 同期をやるなら同時に手に入る

要点は、IndexedDB に移しても「消える」問題は解決しないことです。 ブラウザのサイトデータ消去は、localStorage も IndexedDB もまとめて消します。 容量が足りなくなったときに移す価値はありますが、保持性を上げる手段としては効きません。

そこで今回は File System Access API による実ファイルへの自動書き出しを入れました。 書き出し先を一度決めておけば、以降は 10 件ごとに同じファイルへ上書きされます。 ブラウザのデータごと消えても、そのファイルから丸ごと戻せます。 Chrome / Edge が対応しており、当日の想定環境（Windows のブラウザ）を満たします。

LAN 内で 1 台を親にして複数台で分担する

実現可能。ただし今の 1 台構成を完成させてからで十分です

同梱している serve.js は、いまは静的ファイルを配るだけの Node サーバーです。ここに受付データの保管と配信を足せば、そのまま親機になります。 新しいソフトも、クラウドも、インターネット接続も要りません。

┌─ 親機（受付本部の Windows PC）──────────────────────┐ │ │ │ serve.js │ │ ├─ 静的ファイルの配信 （今もやっている） │ │ ├─ 受付データの保管 （JSON ファイル1本） │ │ └─ 変更の配信 （Server-Sent Events） │ │ │ │ data/reception.json ← 全端末の唯一の正本 │ └────────────────────────┬───────────────────────────────┘ │ Wi-Fi（LAN 内のみ） ┌────────────────┼────────────────┐ │ │ │ 受付端末 A 受付端末 B 表示用モニタ （iPad） （ノートPC） （受付状況を映す）

作りの要点：

  • 正本は親機の 1 ファイルだけ。 各端末は自分の localStorage を持たず、親機に読み書きする。二重管理をしないので、統合作業が要らない
  • 変更の配信は Server-Sent Events。 WebSocket より単純で、ブラウザ標準だけで書ける。ある端末で受付が入ると、他の端末の画面が数百ミリ秒で追随する
  • 親機が落ちても受付は止めない。 各端末は直近の状態を手元に持っておき、通信が切れたら自分の中に貯める。復帰したらまとめて送る（今の LocalStore がそのまま退避先として使える）
  • 定員の取り合いは親機で解決する。 残り1枠に2台から同時に申し込みが来たとき、先に届いた方だけを通す。この判定を端末側でやると必ずずれるので、親機に一本化する

セキュリティ：

  • 大学の共用 Wi-Fi には置かない。 親機で専用のアクセスポイントを立てるか、モバイルルーターを1台用意する。来場者の端末と同じネットワークに受付データを流さないのが一番効く対策です
  • 接続に合言葉を要求する。 端末が親機に繋ぐとき、当日決めた文字列を送らせる。同じ Wi-Fi に入られても、それだけでは読めない状態にする
  • 親機は LAN 内にのみ待ち受ける。 ルーターのポート開放をしない。インターネット側からは存在しないのと同じになる
  • 暗号化は現実的には見送り。 HTTPS にするには証明書が要り、自己署名だと各端末で警告を消す作業が発生します。閉じた LAN で、扱うのが当日限りの氏名と学年であることを踏まえると、ネットワークを分けることの方が費用対効果が高いと判断しています。ここは方針として確認をお願いしたい点です
  • データは当日中に消す。 終了後、親機の JSON と各端末のブラウザデータを消す手順を運用に入れる。残さないのが最も確実な保護です

進め方の提案： まず 1 台での運用を完成させ、実際のオープンキャンパスで 一度回してください。そこで出た「本当に困ったこと」を見てから 2 台目を足す方が、 使われない同期機能を作り込むより確実です。いまの作りは、あとから親機を足せる形に してあります（データの読み書きが local-store.js の 1 箇所に集まっているので、 そこを差し替えるだけで済みます）。

予約の 60 点には意味があります。 学年の最大30点と参加回数の最大20点を足しても 50点にしかならないので、予約した人が予約なしの人に抜かれることは起きません。 「先に予約してくれた人を裏切らない」を、数字の関係として保証しています。 この関係を崩したい場合（予約なしの高3を優先したいなど）は、管理画面で予約の点を 50点未満に下げれば、そのとおりに動きます。
